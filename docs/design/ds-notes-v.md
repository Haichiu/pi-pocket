# Stream V notes: verification and export (`ds/verify`)

## What was built

### `src/server/design/lint.ts` (checks), with `lint-page.ts` and `lint-color.ts`

- **`checkDesign(bundle, system | undefined, options, host, signal): Promise<CheckReport>`**, the contract. It renders in the private Chromium (`withRender`), loads the page, applies the view, runs the steps, and checks. It works with only a `DesignSystem` object (no file reads).
- **`CheckOptions`** (new, in `lint.ts`; `system-types.ts` is untouched): `viewport` (a preset or `{ width, height }`, default desktop), `colorScheme` (`light` | `dark`), `mode` (a system mode; default `dark` for a dark scheme when the system has that mode, else its default mode; a non-default mode also sets `data-theme` on the root when the page sets none), `tweaks`, `page` (another HTML page of the bundle), `actions` (`hover | click | focus` + selector, run first), `slide` (a deck: a slide from 1, or `"all"` up to 40).
- **`checkPage(page, system, view)`**: the same checks on a page already loaded in a `DesignPage`. `design_preview` uses it, so the checks cost no extra render. Also exported: `analyze(raw, tokens)` (pure: no browser), `modeFor`, `reportOf`, `mergeFindings`.
- **`lint-page.ts`** is the script that runs in the page: one walk of the DOM (capped at 4,000 elements and 300 groups for each kind), which returns groups of equal values with a count and the first element. It runs in an **isolated world** (`Page.createIsolatedWorld`), so a page cannot change `getComputedStyle`, `Array.from`, and so on. Its answer is untrusted: `analyze` checks shapes and cuts strings.
- **`lint-color.ts`**: OKLab distance, WCAG contrast, and `tokenSet(system, mode)`: the system's colors, font families, and font-size, spacing, and radius lengths in one mode. Token colors and lengths are resolved **by the browser** (the same canvas path that resolves the page's colors), so every CSS color syntax and `rem`/`clamp()` work, and a token compares with the page like with like.
- Rules (levels): `off-system-color` (error), `off-system-font` (error), `off-system-size` (warning; font size, spacing, radius, each on its own scale), `contrast` (error for text: 4.5, 3 for large text; warning for a form field's edge: 3), `tap-target` (error under 24 px, warning under 44 px; see round 2), `overflow` (error when the page scrolls sideways, warning when `overflow-x: hidden` hides content), `image-alt` (error), `heading-order` (warning), `font-fallback` (error when a declared `@font-face` did not load, warning when a family has no face and is not installed), `missing-viewport` (error; not for decks), `missing-pid` (warning; one finding for the whole page that names the tags; an element needs its own `data-pid`), `focus-visible` (warning).
- Precision choices: the background is the real one (every ancestor's color, opacity, alpha composited over the canvas). Contrast is **not judged** when it cannot be known: a gradient, image, filter, blend mode, or `backdrop-filter` in the chain, text over media or a positioned fill, `background-clip: text`, disabled controls, hidden or 1 px text. Auto and percent margins and padding, pill and circle radii, native checkbox margins, text-link tap targets inside a sentence, a native checkbox without a label, and `0` are not findings. The default black text is not an off-system color. Transitions and animations are switched off while checking, so computed values are resting values. Focus is tested on one element of each kind by really focusing it, and the snapshot covers the element, its descendants, its labels, and siblings and parents three levels up, so a `:focus-visible + .box` pattern counts.
- Equal values in one `data-pid` scope are one finding (round 2): its message ends with `(and N more elements)` (or says `N elements`), and the selector, `pid`, and `rect` are the first element's.
- Suggestions: `off-system-color` names the nearest token (a role beats a palette value when two are as near; a token named for another role is not offered: a border is not a background; none when nothing is within 20); `contrast` names the system color nearest to the text color that passes on that background; `off-system-size` names the nearest step (the smaller one on a tie); `off-system-font` names the font token with the same generic fallback.

### `design_preview`

New arguments: `checks` (default true), `tweaks`, `colorScheme`, `page`, `actions` (up to 10; hover, click, focus; a step that cannot run is a `Note:` and is skipped). The output is the screenshots, then one text: `Checks (mobile, desktop; light; system "Name", mode light): 3 errors, 5 warnings.`, up to 30 findings (errors first, then by rule), `… and N more`, notes, then the console errors and failed requests (the old JSON text is gone; `details.errors` and `details.failedRequests` stay, and `details.checks` holds up to 200 findings for each view). A finding that is in only some of the viewports names them. With actions, the checks run before and after the steps and merge. A system that cannot be read is a note, and the screenshots still come.

### Export fixes

- Deck PNG: `slide` (number from 1) in the tool and the route; `"all"` writes a zip of `slide-N.png` (default path `exports/<id>-v<n>-slides.zip`). `slide` with a non-deck or another format is an error.
- `tweaks` in the tool and the route are applied before the export (CSS custom properties with the knob's unit, plus a `pocket:tweak` event, as the canvas does). The route takes `viewport` as a preset, `WxH`, or `{ width, height }`.
- A page's PDF is as wide as the viewport (paper width and height from the viewport, no margins; an `@page` rule still wins, and decks keep their slide size).
- PPTX: notes leave out `style`, `script`, `template`, `noscript`, and `title` text (`slides()` reads text nodes, not `textContent`); slide images are taken at 2× (3840×2160 for the default slide; no side over 4096 pixels, so very large slides are scaled less).
- Renders hide scrollbars (`Emulation.setScrollbarsHidden`): a tall page's PNG was 15 px narrower than its viewport.

### `render.ts`

- `Slots` (limit, queue, wait): renders **queue** first in, first out instead of failing the third. 2 at once, up to 16 waiting, up to 5 minutes of waiting; a wait ends on abort. The 90 s limit starts when a render starts.
- `DesignPage`: `load(viewport, { scale, page })`, `setScale`, `settle`, `applyView({ colorScheme, theme, tweaks })`, `act(actions)`, `evaluateIsolated`, `pdf(viewport)`. `tweakValues` and `designActions` validate tool and route input.

## What is still weak

- **No real `loadDesignSystem` yet**, so `design_preview` has no off-system rules until T lands (tested with an injected system).
- **Token naming is a guess**: which dimension tokens are the type, spacing, and radius scales comes from path names (`lengthKind` in `lint-color.ts`: `space`, `spacing`, `radius`, `font.size`, `text.*`…). A system that names them otherwise gets no size rule. Worth one look when T's names are final.
- **Gradients are not parsed**: a color inside `linear-gradient()` is not compared with the system, and text on a gradient or image is not judged for contrast.
- **Box shadows, SVG fills, and outlines of the default focus ring** are not compared with the system.
- **Caps**: 4,000 elements and 300 groups for each kind; beyond that the rest is not checked, and the report does not say so.
- **Fluid sizes** (`clamp()` in a page) are compared at the checked viewport only, so a fluid font size is off-system unless a token resolves to the same pixels.
- **Backgrounds come from the DOM chain and rectangle overlap**, not from hit testing (scrolling would change the page), so a sibling overlay is found only when it is positioned or has an image.
- `font-fallback` for a family with no `@font-face` guesses by measuring text, with an allow list of common system fonts; a font installed only on the reader's machine is a warning.
- `focus-visible` focuses one element of each tag-and-class kind (up to 40 kinds, 20 findings), so a state that only some instances lack is missed.
- The preview does not run the checks per slide beyond the slide it shows (`checkDesign` can: `slide: "all"`).

## Round 2: the bench's lint phase (0.772 before, 1.0 after)

Before: precision 0.815, recall 0.733, 5 false findings (2 on clean designs). After: precision 1, recall 1, 0 findings on the clean designs in both color schemes (`node test/design-system-bench/run.ts --only lint`). One suggestion is not the bench's (below); it does not change the score. Every change is a general fix for a cause, with a test; nothing names a design.

Root causes, found in a real browser:

1. **A real bug: the walk skipped `<body>`.** `body.querySelectorAll("*")` does not include the body, so the page's background (almost always on `body`) was never part of the backdrop and every text was judged on white. That gave `title` at 1.18:1 and `lede` at 2.43:1 in the dark runs (light text on a white backdrop). Fix: the body is in the walk. This was the cause of all three contrast false positives on text.
2. **The form-field edge heuristic** (`#name`, 1.40:1) was my own extra rule and is not in the plan or the bench. It is kept only for borders that are not the system's: when every color that makes the edge is a system color, the system owns the look (its contrast pairs are checked by the system validator), so the page is not blamed. A border that is not a system color is still judged.
3. **Tap targets:** the plan says under 24 px is an error and under 44 px a warning, on any viewport. I had added WCAG's spacing exception and a "phone only" condition for the 44 px warning. Both removed. Links inside a sentence stay exempt (WCAG's inline exemption), as does a native checkbox without a label.
4. **One finding for each `data-pid` scope, not for each value.** Equal values were merged across the whole page, so the finding named the first element and the others were lost (`title` `#151a22`, `avatar-img`: same `src` as `hero-img`). The group key now includes the nearest `data-pid`: the same value in one scope is still one finding with a count, in another scope it is another finding. This fits how people and Pi name elements (comments and pins use the pid).
5. **`missing-pid` needs the element's own `data-pid`** (the plan: "a control, heading, image or landmark without its own"). A parent's does not count.
6. **A literal is not a token, even when equal.** `color: #151a22` written in a rule equals `--color-gray-900` in light, but it does not follow the token (dark mode, a change in the system). With a system, the page's own CSS rules and inline styles are read (CSSOM, not computed styles) for colors, lengths (font size, spacing, radius), and font families written without `var()`. A computed value that equals such a literal is reported: an error when it is not a system value, a warning ("written as a literal") with the token to use when it is. `--custom-property` definitions are not uses. Color tolerance for "the same color" is now 1.0 (was 1.5).

Where I disagree with the bench, with evidence: the seeded `banner` expects `color.accent.subtle` or `color.blue.100` for `#e9f0fd`. By OKLab distance the nearest token is `color.bg.subtle` / `gray.100` (`#eceef2`, 1.41) and `blue.100` (`#dce7fb`) is 2.99 away: the color is nearer to the neutral. I report `var(--color-bg-subtle)`, so the bench's suggestion count is 4 of 5. A hue-aware distance (OKLCH with a hue weight) would pick the blue; I did not add one for one case. The integrator decides.

## Round 2b: the held-out result

The integrator's held-out run used the round 1 code, before the fixes above. Its misses are explained by them: the missed tap targets (the spacing exception and the "phone only" condition), the missed off-system colors (a literal that equals a token), and the missed `missing-pid` (a parent's `data-pid` counted). The 11 contrast false findings (8 on clean designs) were the missing `<body>` backdrop: a dark page's text was judged on white.

To prove the contrast rule on other styles, `design-lint.test.ts` has a page of 20 cases ("contrast is judged only where the background is certain"). Judged, with a certain background: light text on a dark section, a white card inside it (and pale text on that card, which is a finding), text in a scope that sets its own variables, a translucent parent over dark, a button label on its own fill, a ghost button. Not judged, because the background is not known: an overlay drawn by `::before` or `::after`, text over an image or a gradient, `backdrop-filter`, `mix-blend-mode`, `clip-path`, a mask, a positioned panel over the text, a parent with partial `opacity`, and screen-reader-only text (`clip`, `clip-path`, `text-indent`, 1 px). A placeholder is never judged (it is not text of the element). Two rules changed for this: partial opacity on the element or an ancestor now means "not known" (before, the faded color was judged), and a positioned or transformed box with a fill counts as something that may cover text.

Also checked: the docs page of the flagship (about 3,000 elements, light and dark, phone and desktop) gives two contrast findings, a swatch label at 3.59:1 and a field edge, both real. Logical properties (`padding-inline`, `border-block-start`) are read as literals too.

## Round 3: suggestions by role, real-world pages, ids, the scheme

1. **Suggestions by role.** The page script now groups a color by how it is used too (text, background, border, outline), so a color used as a background and as text in one scope is two findings, each with its own role. `lint.ts` gives every color token a role from the words of its path (`colorRoleOf`: border, text, background; none for a palette step such as `blue.500`). A text use looks first at text tokens, a background at background tokens, a border at border tokens. A token with no role may stand in. A role token wins when it is within 6 of the best stand-in. Only when no token of the role (or without a role) is within 20 does it offer a token of another role, and then the message says so ("It is a text token, and the system has no background token this close"). Tested with `#1c1e26` used as a background next to a near background token, and with none.
2. **25 real-world pages** are in `test/fixtures/design-lint-pages/` with the findings that I checked by hand (`expected.json`, run by `test/design-lint-pages.test.ts`): utility classes (Tailwind-like), Bootstrap-like markup, a long docs page, a dashboard, a form, marketing pages in light and dark, a blog with an overlay, pricing, chat, kanban, a shop, a newsletter table, custom toggles, a sticky header with a fixed button, a theme set by attribute, `light-dark()`, CSS nesting with layers and container queries, a status table, tabs and an accordion, overlapping avatars, a hero with a background image, an RTL form, a footer; plus the flagship's ten component specimens composed into one page (light and dark). **False findings before: 51 over the runs (3 causes). After: 0.** The causes: (a) a faint token color (`#343b5812`, alpha 0.07) was read from the canvas, which loses digits at low alpha (the token read as `rgb(57 57 85 / 0.07)`, the page's own `rgb(52 59 88 / 0.07)`), so the hover state looked off-system (12 findings): hex and `/ alpha` colors are now read exactly; (b) a specimen of the focus state (class `is-focus`) has its ring at rest, so focusing it changed nothing (36 findings): a focus-named class or `data-focus` is skipped; (c) a 43.99 px box, from fractional text widths, was reported as 44×44 under 44 (3 findings): sizes are compared in whole pixels. Also tightened without a case in the set: a native range slider is a browser control (like a checkbox without a label); hidden overflow of decoration (a glow or blob that runs past the edge and holds no text, control, or image) is not a finding, hidden text is.
   What the pages still report is true: a link 21 px tall inside a flex label, footer links 28 px tall, a page 415 px wide in 390, a `code` with light text on a light fill, a heading level skipped, `Inter` used and not loaded. In the flagship page the code block's inner `pre` and `code` use the browser's `monospace` (the browser's rule beats the component's `font-family` on the parent: a real finding for the flagship), the menu row's hover text is 4.48:1 in dark, and the switch button is 20 px tall.
3. **The scheme.** `test/design-check-scheme.test.ts` calls the dock's route (`system/check`) with `colorScheme` light, dark, and none, on a page whose grey text reads on the light canvas and not on the dark one: light and none give no finding, dark gives the contrast error, and the report names the scheme it ran in.
4. **Ids.** Every finding has `id`: `<rule>-<10 hex>`, a hash of the rule, the scope (the `data-pid`, else the selector), and the value; a repeat in one report gets `-2`. It does not change with the scheme, the viewport, or the wording, so a pin can follow a finding across runs; a changed value is a new id. `CheckFinding.id` is new and optional in `system-types.ts` (one added field), and `cleanReport` in `system-routes.ts` passes it through (one added line): both are other streams' files, for the integrator to check.

5. **Every suggestion is an edit** (second judge). The message names the CSS property, the token, its value, and what it replaces: `Set \`color: var(--color-text-muted)\` (#5a5f73) instead of #7ba3f8.`(the property follows the use:`color`, `background-color`, `border-color`, `outline-color`); `Set \`font-family: var(--font-body)\` instead of Georgia, serif.`; `Set \`padding\` to var(--space-4), 16px, instead of 15px.`(all the properties that hold the value, or`font-size`, `border-radius`); for contrast, the color that passes with its ratio; for a target, `Set \`min-width: 44px; min-height: 44px\``; for a heading, the tag to use; for an image, the `alt`to add.`suggestion`stays the bare`var(--token)`for tools. Covered by "every suggestion is an edit" in`design-lint.test.ts`.

## Round 3b: modes beyond light and dark

`mode` (a name from `system.modes`) is an option of `checkDesign`, and an argument of `design_preview`, `design_export`, and the export route. A named mode: sets `data-theme="<mode>"` on the root before the walk (it replaces a `data-theme` that the page has), draws the page in the mode's scheme (`system.schemes[mode]`; the given `colorScheme` is only the fallback), and compares with that mode's tokens. The name is validated (`The design system has no mode "x". Modes: light, dark, high-contrast.`), and a mode with no system is an error. `modeFor` now returns `{ mode, scheme, theme?, named }`. `CheckReport.mode` is new (optional, `system-types.ts`: for the integrator): the mode compared with, absent without a system; the report's `colorScheme` is the scheme that was drawn. Without a name nothing changes (a dark scheme takes the `dark` mode). Exports now draw in the light scheme unless a mode says otherwise: before, they followed the server's own preference (a dark machine gave a dark PNG). Tested with the flagship's `high-contrast` (drawn dark): the check, the preview (report line and screenshot, also with the checks off), the export tool and route.

## Round 4: the contract for one-tap fixes (written first, for stream U)

```ts
// src/server/design/fix.ts
export function applyExactFixes(
    content: string,
    findings: CheckFinding[],
    system: DesignSystem,
): { content: string; applied: number; skipped: { id: string; reason: string }[] };
```

- `content` is the page's HTML. `findings` are the report's (a finding is **fixable** when it has `fix`, new in `system-types.ts`: `CheckFix { kind, properties, literal, token, cssVar, mode }`; an off-system finding whose literal equals a token exactly has it; U shows a Fix button for these and a Fix all button that passes every fixable finding). `system` is checked again: the token must exist and still equal the literal in `fix.mode`.
- It rewrites only a literal (a color, a `px` length, a whole `font-family` list) that equals the token, only in `<style>` elements and `style` attributes, only in a declaration of a property named by `fix.properties`, and only when the place is certain: an inline style is certain when exactly one element has the finding's `data-pid`; a rule is certain when it is the only one that sets that property to that literal, or its selector is the finding's selector. It never touches scripts, comments, strings, `url()`, `content`, a `var()` fallback, custom property definitions, `@font-face`, `@keyframes`, text, or an attribute that is not `style`.
- The answer is the new HTML, how many replacements were made, and one `{ id, reason }` for each finding that was skipped (`id` is the finding's id). It is a pure function: no browser, no files. A second call with the same findings changes nothing (the literals are gone).
- The value is the same in the mode that was checked and follows the token in the others: say so in the button's text.

### Round 4: what was built

- **`applyExactFixes`** (`src/server/design/fix.ts`), as above. Findings that carry `fix` (new `CheckFix` in `system-types.ts`) are the off-system findings whose literal is a token's to the last digit (a color within 0.3 on the OKLab scale, a length within 0.01 px, a whole `font-family` list). It reads the page with a small scanner (comments, scripts, strings, `url()`, `<textarea>`, `<title>` are skipped; `&quot;` in a `style` attribute counts as a quote) and edits only `<style>` elements and `style` attributes. `applied` counts replacements. Certain places: the inline style of the one element with the finding's `data-pid`; a rule whose selector is the finding's (the selector as written: `.a`, `[data-pid="x"]`); the only place in the page that sets the property to the literal; or several places when at least as many findings with the same literal were given ("fix them together"). Else a skip with the number of places in the reason. Tests: `test/design-fix.test.ts` (hostile pages: the literal in a script, a comment, `content: ""`, a URL, a `var()` fallback, a custom property, `@font-face`, `@keyframes`, a shorthand, `!important`, an entity-quoted font, an unclosed style or comment, a tag hidden in a comment, a 2 MB page, a second call), and a full loop with the browser: check, fix, check again, nothing fixable is left.
  For `U` (done by me, in `system-routes.ts`): `cleanReport` passes `fix` (shape-checked and cut), `mode`, and the new rule `reduced-motion` (also in `RULES` of `check.js`). U calls `applyExactFixes(content, report.findings, system)` and writes the new content as a new version.
- **Reduced motion** (`reduced-motion`, a warning, one finding for the page). The exact rule: an element (not hidden) has a `transition-duration` longer than 500 ms (for a property that is not `none`), or an `animation-duration` longer than 500 ms, or an animation that repeats forever (`animation-iteration-count: infinite`, any speed), and the page's own CSS has no `@media` rule whose condition names `prefers-reduced-motion` (`reduce` or `no-preference`, anything inside it): that rule is taken as "the page thought of it". A style sheet from another origin cannot be read, so the finding is not made when one exists. The message gives the CSS to add: `@media (prefers-reduced-motion: reduce) { *, *::before, *::after { animation-duration: 0.01ms !important; animation-iteration-count: 1 !important; transition-duration: 0.01ms !important; } }`. The value is the longest time (`800ms`), and the element is the first one found. Motion is read before the check's own calm style goes in.
- **Non-text contrast** (WCAG 1.4.11, `contrast`, warnings, 3:1): (1) a form field's edge, as before; (2) the **focus ring**: the ring that the focus draws (an outline, or a spread-only shadow, that was not there at rest; the browser's own `auto` ring is left alone) against what is around it (the parent's backdrop; inside the box for a negative offset); a double ring passes by its best layer; (3) an **icon-only control** (a control with an SVG and no text): the strokes and fills of the icon against the backdrop, judged only when every color it paints fails, and a shape's default black fill counts only when the icon says so. Nothing is judged when the backdrop is not certain (the same rules as text), or when a paint cannot be read (a gradient). With a system, the message names a token that reaches 3:1.
  **A bench conflict, with evidence:** the bench's clean design `clean-pricing` has a hero with `background: var(--color-accent-default)` and a button inside it whose focus ring is `outline: 2px solid var(--color-focus-ring)` (`--color-focus-ring` is `--color-blue-500`, the same blue as the hero): the ring is 1.00:1 against its background, so it cannot be seen. That is a real accessibility defect in a design that the bench calls clean, and the rule reports it (a warning on `hero-cta`; the bench counts two extra findings, one for each scheme). I did not work around it: the design should use an inverse ring in the hero, or the bench should not call it clean. The integrator decides.
- **`check-cli.ts`** (for the docs): `node src/server/design/check-cli.ts <page.html> [--system <folder>] [--mode <name>] [--viewport mobile|tablet|desktop|WxH] [--scheme light|dark] [--json]`. `--system` is a project folder with `.pi/design/`, or that folder itself. The files next to the page are its bundle (at most 200 files, 5 MB each, 20 MB in all; no links, no dot folders, no `node_modules`), so `ds/tokens.css` and images load; with a system, `ds/tokens.css` and `ds/components.css` are added when the folder has none. It runs offline. Exit 0: no error (warnings are printed); 1: at least one error; 2: bad arguments or files. Output: one block for each finding (`level rule selector`, then the message), then one line of totals; `--json` prints the report. In a CI job: `node node_modules/pi-pocket/src/server/design/check-cli.ts site/index.html --system . --mode high-contrast`. Tested in `test/design-check-cli.test.ts`.

## Round 5

1. **Only what the author set is judged.** A value that the browser gives an element by itself is not the page's: a button's border and padding, a heading's size and margins, a link's blue, the default serif, black text (white in a dark page). The page script reads each tag's defaults from a probe of the same tag in a shadow tree (the page's style sheets do not reach it; the probe has the page's `color-scheme`, a link has an `href`, an input has its `type`, and the default font size is the keyword, so that monospace is 13px as it is for the page). A property that is not inherited is the author's when it differs from the tag's default (a length that is the same number of ems as the default is the default); an inherited one (color, font size, font family) when it changes from the parent's to something that is not the tag's default, or is inherited from such a place. This covers colors (text, background, border, outline; a border in the text color is the text color's), font family, font size, spacing, and radii. An unstyled control (no padding, border, or font size of its own: a plain `button`, `input`, `select`, `textarea`, `summary`) is also not judged as a tap target. Contrast is still judged on what is drawn. Tests: `test/design-semantics.test.ts` (a plain button, input, select, textarea, fieldset, hr, details, headings, a link, and code give no finding in light and dark; the same with an author's border, padding, radius, size, and color are judged).
2. **Suggestions: the role first, and honest about change.** A color gets, in this order: a token of its role (text, background, border, from the words of the token's path); a semantic token with no role (an accent); a palette step; any token (with the note that its role differs). A role token wins unless another is more than 12 nearer on the distance scale. When the value changes (not a literal that equals a token), the message says how: `The closest token is #5a5f73, which is darker.` (`slightly`, `much`; or `different in hue, at the same lightness`). A length says `The closest step is 1px smaller.`
3. **Page semantics** (new rules, `system-types.ts`, `RULES`, and the labels of the check list): `missing-lang` (error: no `lang` on `<html>`), `missing-label` (error: a visible field with no `<label>`, `aria-label`, `aria-labelledby`, `title`, or placeholder; hidden, submit, button, reset, and image inputs are exempt), `missing-label` too (error: a link, `role=button`/`link`, button, or summary with no text, `aria-label`, `aria-labelledby`, `title`, label, image `alt`, or SVG title), `missing-main` (warning: no `<main>` or `role=main`; not for a deck). A placeholder counts as a name, so that a finding is a sure one.
4. **`input-zoom`** (warning, only when the viewport is under 600 px wide): a text field (text, email, password, search, tel, url, number), a `textarea`, or a `select` with a font size under 16px. iOS Safari zooms the page in when it gets the focus. The browser's own 13.33px counts, because the page can fix it. With a system the message names the smallest font-size token of 16px or more.
5. **CLI**: `npm run design:check -- <page.html> …` (script `design:check` in `package.json`). `--help` prints the usage and says that it needs Chromium, Chrome, Brave, or Edge (or `PI_POCKET_BROWSER`); without one the exit code is 2.
6. **`lint-page.ts` is split by concern**, with no change in behavior (the script string is byte for byte what it was, checked before the split): `lint-page.ts` (types and the order of the parts), and the parts `-setup` (the input, helpers, the motion scan, the calm style), `-values` (colors, the system's values, selectors, groups, and what the author set), `-literals` (what the page wrote as literals), `-states` (the backdrop behind each element), `-elements` (the per-element walk), `-checks` (images, semantics, tap targets, overflow, headings, fonts), `-focus` (icons, focus rings, the answer). They are one function body; the order is fixed.

What the flagship page shows now (true findings): the input specimen is 13px (`input-zoom` on a phone), and the code block's inner `pre` is the browser's monospace.

### Round 5, second part (held-out set 3: precision 0.055, 96 false findings, almost all browser defaults)

- **The rule is now exact: a value that no author CSS sets is never an off-system finding.** With the page's rules known, "set by the author" is a fact about them, not a guess from the browser's defaults: the page script collects every style rule of the page (style elements, linked sheets, `@import`, active `@media` and `@supports`; up to 4,000), indexes them by the id, class, or tag of each selector's last compound, and asks, for each element and property, whether a rule that matches it, or its `style` attribute, sets that property (or a shorthand or logical form of it: `padding` for `padding-top`, `border` for `border-top-color`, `font` for `font-size`, `all`). A property that is inherited (color, font size, font family) counts when the element sets it, or when it keeps its parent's value and the parent's was set by the author; a value that differs from the parent's with no rule behind it is the browser's (a link's blue, a nested `h1`'s size, which the probe could not know). Nested `h1` (18.7px), `button`/`input` faces, `td` padding, `fieldset`, lists, and the legacy markup (`<font color>`, `cellpadding`, `bgcolor`) are no longer reported; the page `test/design-semantics.test.ts` keeps all of these on purpose and is clean in light, dark, phone and desktop.
- **A sheet linked from the bundle is now read.** The sandbox makes the render's own server another origin, so the browser refused to show the rules of a linked sheet (this also hid literals and `prefers-reduced-motion` rules in linked sheets). The script now fetches the sheet's text and parses it with a constructed sheet. A sheet that cannot be read at all (another site's: the check is offline) makes the rules unknown; the browser's defaults (the probe from the first part, and no legacy markup) then stand in, so the plain page stays clean. The motion rule says nothing when a sheet is unreadable, as before.
- **Rule names, as the integrator asked:** `missing-lang` (no `lang` or an empty one on `<html>`) and `missing-label` (a field, button, link, or switch with no accessible name: label, `aria-label`, `aria-labelledby`, `title`, text for buttons and links, an image's `alt`, an SVG title; a button inside a label is named by it). They replace my `form-label` and `accessible-name`. `missing-main` stays (a warning). The names (with `missing-main`) are in `CheckRule` (`system-types.ts`), `RULES` of `system-routes.ts`, and the labels of `check.js`. The switch and the other ARIA widget roles (`switch`, `checkbox`, `radio`, `tab`, `menuitem`) are in the check.

### Round 5, third part (the three rulings)

- **A placeholder is not a label** (WCAG 1.3.1, 3.3.2). A field whose only name is its placeholder is a `form-label` error; the message says to add a `<label>` or an `aria-label`. A `title` still names a field (the last resort in WCAG).
- **ARIA widgets need a name.** `accessible-name` (error): a link, button, summary, `role=button`, `link`, `switch`, `tab`, `menuitem`, `menuitemcheckbox`, `menuitemradio`, or `option` with no text, `aria-label`, `aria-labelledby`, `title`, label, image `alt`, or SVG title. `form-label` (error): a `role=textbox`, `searchbox`, `combobox`, `slider`, `spinbutton` (their content is their value, so it does not name them), or a `role=checkbox` or `radio` with neither a name nor text. The rule names are `form-label` and `accessible-name` again, as in this ruling (superseded: see the fourth part, one `missing-label`).
- **`input-zoom` judges only a font size that the author set** (the same test as the off-system values, `inheritedAuthored`). The browser's 13.33px on an unstyled field is not the size that iOS goes by. A styled field under 16px on a viewport under 600px stays a warning.

### Round 5, fourth part (one `missing-label` again; longhands)

- **Rule names, final:** the bench uses `missing-label`, `missing-lang`, and `missing-main`, so `form-label` and `accessible-name` are gone again and `missing-label` is the one rule for a field, an ARIA widget, a link, a button, a tab, a menu item, a switch, or a summary with no name (the message tells a field, "has no label", from the others, "has no accessible name"). A placeholder is not a name; `input-zoom` judges only a size the author set (also `font: inherit` of a smaller size).
- **A longhand that no author rule sets is the browser's.** The author index used one setter list for a whole family, so one `margin-top` made `margin-bottom` look authored (the paragraph's own 1em, 14px, was reported). Each computed longhand now has its own list of properties that set it: itself, the shorthands that carry it (`margin`, `border`, `border-color` for a color, `border-top`, `border-top-color`, `border-radius`, `gap`, `grid-gap`, `outline`, `background`, `font`, `all`), and the logical forms of its side (`margin-block-end`, `margin-block`, `padding-inline-start`, `border-inline-end-color`, `border-start-start-radius`; left and right swap in a right-to-left page). `inset` is not judged. The test sets one longhand at a time (and a shorthand, and the logical forms) and checks that only what the author set is judged.

### Round 5, final names

**Final decision of the integrator: the rules are `form-label` (a field, or a widget that stands in for one: textbox, searchbox, combobox, slider, spinbutton, checkbox, radio) and `accessible-name` (a link, button, summary, tab, menu item, option, or switch), plus `missing-lang` and `missing-main`. There is no `missing-label`.** Everything above that says `missing-label` is superseded. A placeholder is not a name; the longhand fix of the fourth part stays.

### Round 6 (stopped at the wrap-up; what is in)

- **Suggestions** (`lint-suggest.ts`): an exact match wins (a role token, an accent, a palette step, another role's token, a component's last); otherwise the nearest token of the use's role in the hue family (OKLCH: a hue limit, a share of the chroma, a neutral for a neutral, of the system's own neutral hue); never a component's token for a color that no token equals; a failing contrast gets a passing token of its hue, else a text token and the message says the hue changes; "the same color" is said only for the same 8-bit value.
